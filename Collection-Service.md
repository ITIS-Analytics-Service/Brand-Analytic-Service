# Collection Service

## 1. Назначение

**Collection Service** — микросервис, отвечающий за сбор публикаций из выбранных интернет-источников по ключевым словам, связанным с отслеживаемым брендом.

Сервис выполняет следующие задачи:

- хранит настройки сбора публикаций;
- запускает сбор по расписанию или по запросу пользователя;
- координирует работу компонентов, взаимодействующих с источниками;
- получает публикации и приводит их к единому формату;
- передаёт собранные публикации в Kafka для последующей обработки;
- сохраняет историю запусков и информацию об ошибках.

Collection Service отвечает за получение исходных данных. Проверка релевантности публикаций, устранение дубликатов на уровне обработанных данных, определение тональности и подготовка аналитики относятся к Processing Service.

## 2. Основные компоненты

### 2.1. REST API

Предоставляет HTTP-интерфейс для взаимодействия с Frontend.

Основные обязанности:

- получение и изменение настроек мониторинга;
- получение списка доступных источников;
- ручной запуск сбора публикаций;
- получение истории запусков и информации об их статусе.

REST API не выполняет сбор самостоятельно. При запросе на запуск он инициирует работу Collection Orchestrator.

### 2.2. Monitoring Configuration

Представляет настройки, определяющие правила сбора публикаций.

Настройки включают:

- идентификатор бренда;
- название бренда;
- ключевые слова и варианты написания;
- список выбранных источников;
- интервал автоматического сбора;
- признак активности мониторинга.

Настройки хранятся в PostgreSQL и используются при запуске сбора.

На первом этапе система ориентирована на один отслеживаемый бренд на пользователя. Модель данных не должна препятствовать дальнейшему расширению до нескольких брендов.

### 2.3. Scheduler

Отвечает за автоматический запуск сбора в соответствии с настройками мониторинга.

Основные обязанности:

- определение времени следующего запуска;
- проверка активности мониторинга;
- инициирование сбора через Collection Orchestrator;
- предотвращение случайного одновременного запуска нескольких одинаковых заданий.

Scheduler не взаимодействует с интернет-источниками напрямую и не обрабатывает публикации.

Расписание должно сохранять корректность после перезапуска приложения. Для этого состояние расписания и время предыдущих запусков необходимо согласовать с данными, хранящимися в PostgreSQL.

### 2.4. Collection Orchestrator

Координирует выполнение одного запуска сбора публикаций.

Основные обязанности:

1. Получение настроек мониторинга.
2. Создание записи `CollectionJob`.
3. Определение источников, участвующих в запуске.
4. Инициирование сбора через соответствующие компоненты.
5. Получение результатов и информации об ошибках.
6. Передача собранных публикаций на нормализацию и отправку в Kafka.
7. Обновление итогового статуса запуска.

Orchestrator используется как при автоматическом запуске через Scheduler, так и при ручном запуске через REST API.

### 2.5. CollectionJob

`CollectionJob` — запись, описывающая один запуск сбора публикаций.

Она необходима для хранения истории запусков, отслеживания ошибок и отображения состояния сбора пользователю.

Основные атрибуты:

- `id` — идентификатор запуска;
- `brandId` — идентификатор отслеживаемого бренда;
- `reason` — причина запуска (`SCHEDULED` или `MANUAL`);
- `status` — текущий статус;
- `startedAt` — время начала;
- `finishedAt` — время завершения;
- `collectedCount` — количество собранных публикаций;
- `errorMessage` — общая информация об ошибке, если применимо.

Предусмотренные статусы:

- `PENDING` — запуск создан, но ещё не начат;
- `RUNNING` — сбор выполняется;
- `COMPLETED` — сбор успешно завершён;
- `PARTIALLY_COMPLETED` — часть источников завершилась с ошибками;
- `FAILED` — сбор не удалось выполнить.

`collectedCount` отражает количество публикаций, полученных Collection Service. Оно не обязательно совпадает с количеством уникальных и релевантных упоминаний после обработки.

Для отслеживания результата работы отдельных источников может использоваться сущность `CollectionJobSource`, содержащая идентификатор источника, статус, количество полученных публикаций и сведения об ошибках.

### 2.6. Search Provider

Дополнительный компонент для источников, где поиск публикаций выполняется через внешний поисковый сервис или API.

Он может возвращать ссылки на найденные публикации и доступные метаданные.

Search Provider не является обязательным для каждого источника. Если конкретный источник самостоятельно предоставляет необходимые публикации через API или RSS, отдельный поисковый компонент может не потребоваться.

### 2.7. Source Collectors

Отвечают за получение публикаций из конкретных источников.

В зависимости от возможностей источника сбор может выполняться через:

- API;
- RSS-ленты;
- web scraping;
- внешний поисковый API с последующим получением страниц, если это необходимо.

Каждый Collector учитывает особенности своего источника и возвращает полученные данные в формате, пригодном для дальнейшей нормализации.

Набор поддерживаемых источников определяется возможностями доступа к данным и объёмом работ MVP. Система не гарантирует обнаружение всех упоминаний во всём интернете.

### 2.8. Normalizer / DTO Mapper

Приводит данные, полученные из разных источников, к единому DTO `RawMention`.

Компонент отвечает за:

- сопоставление полей источника с полями DTO;
- нормализацию представления даты и времени;
- заполнение идентификатора источника и контекста бренда;
- корректную обработку отсутствующих необязательных полей.

Нормализация не включает определение тональности и окончательную оценку релевантности публикации.

### 2.9. Kafka Producer

Отправляет нормализованные публикации в Kafka для последующей обработки Processing Service.

Используемый топик: `raw-mentions`.

Одна публикация передаётся одним сообщением. Например, если в рамках запуска найдено 37 публикаций, сервис отправляет 37 сообщений.

Producer должен учитывать возможные ошибки отправки и не считать передачу данных успешно завершённой до подтверждения отправки. Механизм восстановления публикаций, которые были получены, но не отправлены, должен быть определён при проектировании надёжной доставки.

## 3. DTO RawMention

`RawMention` — структура данных, описывающая одну собранную публикацию.

Предварительный состав полей:

| Поле | Назначение |
|---|---|
| `eventId` | Идентификатор события передачи публикации |
| `jobId` | Идентификатор запуска, в рамках которого получена публикация |
| `brandId` | Идентификатор отслеживаемого бренда |
| `sourceId` | Идентификатор источника |
| `externalId` | Идентификатор публикации во внешнем источнике, если доступен |
| `url` | Ссылка на публикацию |
| `title` | Заголовок публикации, если доступен |
| `text` | Текст публикации, если доступен |
| `author` | Автор публикации, если известен |
| `publishedAt` | Время публикации |
| `collectedAt` | Время получения публикации системой |

Поля, которые источник не предоставляет, должны допускать отсутствие значения.

`eventId` идентифицирует сообщение, а `externalId` идентифицирует исходную публикацию в пределах источника. Эти идентификаторы имеют разные назначения.

`jobId` позволяет связать публикацию с конкретным запуском сбора и упростить диагностику.

## 4. Хранение данных

Для MVP используется PostgreSQL. Данные, которыми владеет Collection Service, логически отделены от данных Processing Service.

Основные сущности:

- `MonitoringConfig` — настройки мониторинга;
- `CollectionJob` — история запусков;
- `CollectionJobSource` — результаты выполнения по отдельным источникам.

Collection Service отвечает за создание и изменение этих записей.

Обработанные упоминания и результаты анализа принадлежат Processing Service. Collection Service не должен напрямую изменять данные, принадлежащие Processing Service.

Для MVP допускается использование одного экземпляра PostgreSQL с логическим разделением областей хранения. При этом логическое владение данными должно оставаться разделённым между сервисами.



## 5. REST API

Предварительный список endpoints:

| Метод | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/v1/monitoring-config` | Получить настройки мониторинга |
| `PUT` | `/api/v1/monitoring-config` | Создать или обновить настройки |
| `GET` | `/api/v1/sources` | Получить список доступных источников |
| `POST` | `/api/v1/monitoring-jobs` | Запустить сбор вручную |
| `GET` | `/api/v1/monitoring-jobs` | Получить историю запусков |
| `GET` | `/api/v1/monitoring-jobs/{jobId}` | Получить информацию о запуске |

Ручной запуск создаёт фоновое задание. При успешном принятии запроса API возвращает `202 Accepted` и идентификатор `CollectionJob`. Клиент может использовать этот идентификатор для последующего получения статуса.

Автоматические запуски инициируются Scheduler и не требуют отдельного HTTP-запроса от пользователя.

## 6. Основной сценарий работы

1. Пользователь настраивает ключевые слова, источники и интервал сбора через Frontend.
2. REST API сохраняет настройки в PostgreSQL.
3. Scheduler определяет, что наступило время очередного запуска, либо пользователь инициирует запуск вручную.
4. Collection Orchestrator создаёт `CollectionJob` и определяет список источников.
5. Source Collectors получают публикации из выбранных источников. При необходимости используется Search Provider.
6. Normalizer приводит результаты к структуре `RawMention`.
7. Kafka Producer отправляет отдельное сообщение для каждой публикации в топик `raw-mentions`.
8. Collection Orchestrator фиксирует итоговый статус запуска и результаты работы источников.
9. Processing Service независимо получает сообщения из Kafka и выполняет дальнейшую обработку.

## 7. Обработка ошибок

Collection Service должен учитывать следующие ситуации:

- источник временно недоступен;
- внешний сервис возвращает ошибку или ограничивает частоту запросов;
- один источник завершает работу с ошибкой, а остальные работают успешно;
- полученные данные не удаётся нормализовать;
- Kafka недоступна или отправка сообщения завершается ошибкой;
- повторный запуск пересекается с уже выполняющимся заданием.

Ошибка одного источника не должна автоматически приводить к потере результатов остальных источников.

Статус `PARTIALLY_COMPLETED` позволяет отразить частичный успех сбора. Ошибки и результаты отдельных источников должны быть доступны для диагностики.

Конкретные механизмы повторных попыток, ограничения параллелизма и восстановления неотправленных публикаций определяются на этапе детального проектирования.

## 8. Границы ответственности

Collection Service отвечает за:

- конфигурацию сбора;
- планирование и запуск заданий;
- взаимодействие с источниками;
- получение и нормализацию публикаций;
- передачу публикаций в Kafka;
- историю запусков и диагностику ошибок сбора.

Collection Service не отвечает за:

- определение тональности публикаций;
- окончательную оценку релевантности;
- аналитические показатели и графики;
- пользовательское отображение результатов;
- обработку и хранение результатов анализа, принадлежащих Processing Service.

## 9. Состав MVP

В первую версию входят:

- настройка бренда, ключевых слов и источников;
- автоматический запуск сбора по расписанию;
- ручной запуск сбора;
- поддержка ограниченного набора доступных источников;
- создание и отслеживание `CollectionJob`;
- нормализация публикаций в `RawMention`;
- отправка публикаций в Kafka;
- сохранение статусов запусков и ошибок.

Сложная инфраструктура технического мониторинга, расширенные механизмы восстановления, поддержка множества брендов на одного пользователя и дополнительные способы сбора могут быть добавлены позднее.
