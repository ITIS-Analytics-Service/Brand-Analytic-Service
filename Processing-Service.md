# Processing Service

## 1. Назначение

**Processing Service** — микросервис, отвечающий за обработку публикаций, собранных из внешних источников, анализ их содержания и предоставление подготовленных данных для аналитики бренда.

Сервис получает необработанные публикации от Collection Service через Apache Kafka, проверяет и нормализует данные, устраняет дубликаты, определяет тональность текста с помощью отдельного ML-сервиса и сохраняет результаты в PostgreSQL.

Также Processing Service предоставляет REST API для получения аналитических показателей и списка обработанных публикаций.

## 2. Основные обязанности

- Получение событий с публикациями из Kafka.
- Проверка корректности входных данных.
- Нормализация идентификаторов и URL для дедупликации.
- Обнаружение повторных публикаций.
- Очистка и подготовка текста к анализу.
- Определение тональности публикаций с помощью ML-сервиса.
- Сохранение публикаций и результатов обработки в PostgreSQL.
- Предоставление REST API для Frontend.
- Обеспечение идемпотентности, обработка ошибок и повторных попыток.

Сервис не отвечает за поиск публикаций в интернете, расписание сбора и управление настройками мониторинга. Эти задачи выполняет Collection Service.

## 3. Взаимодействие с другими компонентами

### Collection Service

Передаёт необработанные публикации в Kafka после их обнаружения во внешних источниках. Processing Service не обращается к Collection Service за каждой публикацией: обмен данными происходит через события.

### Apache Kafka

Используется для асинхронной передачи публикаций. Основной топик — `raw-mentions`.

Каждое сообщение содержит данные одной публикации в формате `RawMention`.

### ML Service

Отдельный небольшой сервис на Python, предоставляющий готовую модель для анализа тональности русскоязычных текстов.

Processing Service отправляет ему подготовленный текст и получает результат классификации. ML Service выполняет инференс модели, но не отвечает за сбор публикаций, дедупликацию, хранение основных данных и бизнес-аналитику.

### PostgreSQL

Хранит обработанные публикации, их исходные поля и результаты анализа. База данных является основным источником данных для аналитических REST-запросов.

### Frontend

Получает через REST API агрегированные показатели и список публикаций с фильтрами. Frontend не обращается к PostgreSQL или ML Service напрямую.

## 4. Основной процесс обработки публикации

1. Получить сообщение `RawMention` из Kafka.
2. Проверить обязательные поля и допустимость данных.
3. Нормализовать идентификаторы и URL, необходимые для дедупликации.
4. Проверить, не была ли публикация ранее сохранена для данного бренда и источника.
5. При обнаружении дубликата не создавать повторную запись.
6. Очистить текст от HTML-разметки и технических элементов, не удаляя значимые для смысла части текста.
7. Передать подготовленный текст в ML Service.
8. Получить предсказанную тональность: `POSITIVE`, `NEGATIVE` или `NEUTRAL`.
9. Сохранить публикацию и результат анализа в PostgreSQL.
10. Завершить обработку сообщения с учётом используемого механизма подтверждения Kafka.

Для устойчивой дедупликации используется идентификатор внешней публикации, если он доступен. В противном случае применяется нормализованный URL. Уникальность должна обеспечиваться также ограничениями базы данных.

## 5. ML Service

ML Service реализуется отдельно на Python и использует готовую модель, подходящую для русскоязычных публикаций.

### Входные данные

Подготовленный текст публикации.

### Выходные данные

- Предсказанная тональность: `POSITIVE`, `NEGATIVE` или `NEUTRAL`.
- Уверенность предсказания, если модель предоставляет соответствующие вероятности.

ML Service не обучает собственную модель на первом этапе проекта. Выбор конкретной модели будет зависеть от качества классификации, требований к ресурсам, скорости обработки и условий использования модели.

## 6. Хранение данных

Основная таблица — `mentions`.

Предварительный набор полей:

- `id` — внутренний идентификатор публикации.
- `brand_id` — идентификатор отслеживаемого бренда.
- `source_id` — идентификатор источника.
- `external_id` — внешний идентификатор публикации, если доступен.
- `url` — ссылка на публикацию.
- `title` — заголовок.
- `text` — текст публикации.
- `author` — автор, если известен.
- `published_at` — время публикации.
- `collected_at` — время сбора.
- `sentiment` — результат анализа тональности.
- `topic` — тема публикации, если классификация тем включена.
- `processed_at` — время успешной обработки.

Окончательная схема таблицы и стратегия повторной обработки сообщений уточняются при проектировании базы данных.

## 7. REST API

Processing Service предоставляет API для аналитики и просмотра публикаций.

Предварительные группы эндпоинтов:

- `GET /api/brands/{brandId}/analytics/summary` — сводные показатели за период.
- `GET /api/brands/{brandId}/analytics/timeline` — динамика количества упоминаний.
- `GET /api/brands/{brandId}/analytics/sentiment` — распределение тональности.
- `GET /api/brands/{brandId}/mentions` — список публикаций с фильтрами по датам, источнику и тональности.

Для списка публикаций предусматриваются пагинация и сортировка. Аналитические запросы используют данные, уже сохранённые в PostgreSQL.

## 8. Обработка ошибок и надёжность

- Повторная доставка Kafka-сообщения не должна создавать дубликат.
- Временные ошибки ML Service и базы данных должны обрабатываться с ограниченными повторными попытками.
- Некорректные сообщения должны регистрироваться и не приводить к бесконечному циклу повторной обработки.
- Сохранение данных и подтверждение сообщения Kafka должны быть организованы так, чтобы сбой не приводил к потере публикации.
- При необходимости для сообщений, которые не удалось обработать после повторных попыток, используется dead-letter topic.
- Для временно недоступного ML Service предусматривается стратегия восстановления и повторного анализа.

## 9. Границы первой версии

В первую версию входят получение публикаций из Kafka, валидация, нормализация, дедупликация, анализ тональности, сохранение данных и базовые аналитические REST-эндпоинты.

Классификация тем, поиск семантически похожих публикаций, история версий анализа и более сложные ML-механизмы могут быть добавлены позднее.

## 10. Технологии

- Java и Spring Boot — основная бизнес-логика Processing Service.
- Apache Kafka — асинхронный обмен событиями.
- PostgreSQL — хранение публикаций и результатов анализа.
- Python — отдельный ML Service.
- Готовая ML-модель — определение тональности русскоязычных текстов.
- REST API — взаимодействие с Frontend и вызов ML Service.
